Professional Git Flow Strategy

Standard Operating Procedure for 2-Developer Teams

⚠️ CRITICAL RULE: Never push or commit directly to the main or develop branches. All code must be written in a feature/ branch and merged via GitHub Pull Requests.

1. The Core Branches

Your repository should only have two permanent, long-living branches. All other branches are temporary.

main

The Production Branch. This code is what runs on the live server. It must always be 100% stable and working.

develop

The Integration Branch. Both developers merge their finished features here. This is used for staging and testing the MVP.

2. The Daily Developer Workflow

  • Sync with the Team

    Always start your day by pulling the latest code that your teammate merged into develop.

    git checkout develop
git pull origin develop

  • Create a Feature Branch

    Create a temporary branch just for the specific task you are working on.

    # Naming convention: feature/name-of-task
git checkout -b feature/catalog-api

  • Write Code & Commit

    Write your code, save your files, and commit your work regularly.

    git add .
git commit -m "feat: added catalog and products api endpoints"

  • Push to GitHub

    Send your completed feature branch to the remote repository.

    git push -u origin feature/catalog-api

3. Code Review & Merging (GitHub)

Once you push your feature branch, you must not merge it from your terminal. Follow this process:


  1. Developer A logs into GitHub.com.
  2. Clicks the green "Compare & pull request" button for their new branch.
  3. Sets the Base branch to develop (not main).
  4. Developer B gets notified, reviews the code changes on GitHub, and clicks "Approve".
  5. Developer A clicks "Merge pull request".
  6. Developer A deletes the temporary feature branch from GitHub.
